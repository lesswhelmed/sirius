# Ship the Sirius iOS app to App Store Connect

This is an **Expo managed + EAS Build** app (`apps/mobile`). There is no local Xcode
archive step — release builds run in EAS cloud and submission goes through `eas submit`.
The `ios/`/`android/` dirs are gitignored and regenerated by `expo prebuild`; never
commit them or build locally.

## What is and isn't automatable (read this first)

A "deploy" is NOT one non-interactive command. It splits into three lanes — know which
one each step lives in before promising the user a hands-off run:

- **Agent-safe lane (fully automatable here):** preflight (db:generate, mobile
  typecheck, clean-tree assertion, native-AI verify), listing existing builds, kicking
  the EAS production build, polling it to a terminal state, and cross-checking the
  server URL + docs. Part 2 runs all of this.
- **Conditionally automatable lane:** `eas submit`. It is non-interactive **only** when
  App Store Connect API-key env vars are present in the shell (see Part 3). Without
  them, `eas submit` requires an **interactive Apple ID login + 2FA** — a human must run
  it. The bundled script auto-detects which case applies.
- **Human-required lane (never automatable from here):** everything in the App Store
  Connect web UI and on a physical device — age-rating questionnaire, attaching the
  IAP/subscription to the version, capturing the reviewer screen recording, filling App
  Review notes, posting the Resolution Center reply, and the final **Submit for Review**.
  Apple gates these behind the account UI; the skill's job is to prep them and hand
  over exact text/commands, not to click them.

**So: full "no-interaction" deployment is only possible if the user has provisioned an
ASC API key AND all store metadata is already complete AND they accept auto-submit.**
Otherwise, build automatically, then hand off. Don't fake the human steps.

## Part 0 — Decide scope with the user first

Shipping a build consumes an EAS build; auto-submitting uploads a public binary. Neither
is cheaply reversible. Before doing anything, confirm three things — don't guess (this
matches the user's standing instruction to ask before irreversible/outward actions):

1. **Fresh build vs. reuse an existing FINISHED build?** A fresh build picks up the
   latest `main`; reuse is faster but may be stale. Check history first:
   `cd apps/mobile && bunx eas-cli build:list --platform ios --limit 5 --non-interactive --json`.
2. **How far to take it:** build only, or build + submit? Map their answer to a lane:
   - build only → `BUILD_ONLY=1 <script>`
   - build + submit, human does Apple login → default script run, then hand off
   - build + fully non-interactive submit → only if they've provided an ASC API key
3. **Submit auth:** interactive Apple login (default) or an App Store Connect API key
   (`.p8` + Key ID + Issuer ID) for non-interactive submit.

## Part 0.5 — Bump the marketing version FIRST (mandatory for every post-release build)

**Every** production build made after a version has been submitted to Apple MUST carry a
**higher** `CFBundleShortVersionString` than the last version that reached the store — or
the upload dies at `eas submit` time (a full ~25-min cloud build wasted first, because the
build itself SUCCEEDS and only Apple's delivery step rejects it):

- `ITMS-90186` — *"The train version 'X' is closed for new build submissions."* Once a
  version is approved/released, its **pre-release train is closed to ALL new builds —
  including TestFlight.** You cannot sneak another build into it, not even for testers.
- `ITMS-90062` — *"CFBundleShortVersionString must contain a higher version than the
  previously approved version."*

`autoIncrement`/`appVersionSource: remote` do **not** save you here — they only bump the
**build number**, not the marketing version. The marketing version is `apps/mobile/app.json`
→ `expo.version`, and it is a manual edit.

**Do this before Part 2, on every release:**

1. Check what's live: `cd apps/mobile && bunx eas-cli build:list --platform ios --limit 5 --non-interactive --json` (look at `appVersion`), or the App Store Connect **Versions** list.
2. Bump `apps/mobile/app.json` → `expo.version` to a higher value (patch e.g. `1.0.1 → 1.0.2` for fixes; minor e.g. `1.0.1 → 1.1.0` to headline a feature).
3. **Commit it** (`requireCommit: true` builds the committed tree): `git commit -- apps/mobile/app.json -m "chore(mobile): bump iOS marketing version to <X>"`.

The bundled build script now enforces this: **preflight 1/5** hard-stops if `app.json`'s
version equals the last FINISHED production build's `appVersion` (override only for a
version that was never uploaded to Apple: `ALLOW_SAME_VERSION=1`). Don't defeat the guard
to "just get a build out" — bump the version, that's the fix.

> **Incident (2026-07-09):** shipped a build reusing `1.0.1` (already live) straight to
> `eas submit`; Apple rejected it with ITMS-90186 + ITMS-90062 after the cloud build had
> already finished. Root cause: no version bump + no pre-build guard. Fixed by adding the
> preflight guard above.

## Part 1 — Verify the server URL (lesswhelmed.com)

The mobile production build must talk to `https://lesswhelmed.com`, and the prod server
must trust the app's `siriusapp://` auth callback. These are already set — confirm they
haven't drifted:

- `apps/mobile/eas.json` → `build.production.env.EXPO_PUBLIC_AUTH_BASE_URL` = `https://lesswhelmed.com`
- `.env.production` → `BETTER_AUTH_URL`, `NEXT_PUBLIC_BETTER_AUTH_URL`,
  `EXPO_PUBLIC_AUTH_BASE_URL` all = `https://lesswhelmed.com`, and
  `AUTH_TRUSTED_ORIGINS` contains `siriusapp://`

If a different prod URL is ever requested, change it in **all** of those places (the
single source of truth for dev hosts is `packages/auth/dev-hosts.js`, but the prod URL
lives in eas.json + `.env.production`). Note `apps/mobile/.env` holds the **dev** URL
(`https://sirius.local`) — leave it alone; it is not used by store builds.

## Part 2 — Preflight + build + submit-or-handoff (agent-safe)

Run the bundled script from the repo root. It runs `db:generate`, typechecks the mobile
app, asserts a clean committed tree, runs the `verify:native-ai` gate, kicks the EAS
production build, and polls until it reaches a terminal state (printing the build URL so
the human can watch logs). Then it either submits non-interactively (if ASC API-key env
vars are present) or prints the exact interactive-submit command to hand off.

```sh
# build → poll → submit (non-interactive) or print the handoff command
.claude/skills/ios-app-store-deploy/scripts/build-ios-prod.sh

# build → poll only, then stop
BUILD_ONLY=1 .claude/skills/ios-app-store-deploy/scripts/build-ios-prod.sh

# skip building; act on the latest FINISHED production build (reuse path)
REUSE_LATEST=1 .claude/skills/ios-app-store-deploy/scripts/build-ios-prod.sh
```

It is safe to re-run. If typecheck fails or the tree is dirty, it stops **before**
consuming a build — fix the issue at the source (don't work around it) and ask before
changing build config. If the EAS build itself **ERRORS**, open the printed build-logs
URL, read the failing phase, and fix the root cause — confirm against the real log
before changing anything.

## Part 3 — Submit to App Store Connect

Because `ascAppId` + `appleTeamId` are already in `eas.json`, submit is turnkey once the
Apple auth is cleared. Two paths:

**Interactive (default — human runs it):**

```sh
cd apps/mobile && bunx eas-cli submit --profile production --platform ios --latest
# or target a specific build: --id <build-id>
```

Signs in with the Apple ID on Team `L7U86T3YRV` (+ 2FA), uploads the `.ipa`, and ASC then
"processes" it (a few minutes to ~1 hr) before it can be attached to a version.

**Non-interactive (only if the user provides an ASC API key):**

```sh
cd apps/mobile
EXPO_APPLE_API_KEY_PATH=/path/AuthKey_XXXX.p8 \
EXPO_APPLE_API_KEY_ID=XXXXXXXXXX \
EXPO_APPLE_API_ISSUER_ID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx \
bunx eas-cli submit --profile production --platform ios --latest --non-interactive
```

The bundled script does this automatically when all three vars are set. **Manual
fallback:** download the `.ipa` from the EAS build page and upload via **Transporter**
(Mac App Store) — slower; only if `eas submit` misbehaves.

## Part 4 — Human-required lane (App Store Connect + device)

`eas submit` only uploads the binary. To actually get into review, a human must, in the
App Store Connect web UI and on a physical device:

- Set/confirm **Age Rating** (incl. User-Generated Content = Yes — the Friends feed ships
  UGC), category, and any content-rights answers.
- Attach the **subscription/IAP** ("Sirius AI Pro") to the version if ASC asks.
- Fill **metadata + screenshots** (drafted in `APP_STORE_SUBMISSION.md` §7–§8), the
  reviewer demo account, and **App Review Information → Notes**.
- Capture the **physical-device screen recording** Apple asked for (terms gate → report →
  block), attach it to the notes.
- Post the **Resolution Center reply** (ready-made text in `APP_STORE_SUBMISSION.md` §12).
- Click **Add for Review → Submit** (Manual release recommended for a first launch).

Prep these by surfacing the exact text/commands from the docs below; don't claim they're
done until the human confirms the ASC UI is complete.

## What "done" means (per lane)

- **Build-only done:** a `FINISHED` EAS production build exists (id + logs URL known).
- **Submit done:** the binary is uploaded and "processing"/available in App Store Connect.
- **Review-ready handoff done:** the human has the ASC checklist, recording shot list,
  reviewer notes, and the Resolution Center reply text (all from the docs above).
- **Submitted for review:** only true after the **human** confirms they completed the ASC
  UI steps and clicked Submit. The skill cannot assert this itself.
