# Ship the Sirius iOS app to App Store Connect

This is an **Expo managed + EAS Build** app (`apps/mobile`). There is no local Xcode
archive step — release builds run in EAS cloud and submission goes through `eas submit`.
The `ios/`/`android/` dirs are gitignored and regenerated by `expo prebuild`; never
commit them or build locally.

The flow has three parts. Parts 1–2 are automatable here. Part 3 (`eas submit`) needs
an interactive Apple login, so by default we prep it and hand the command to the human —
unless they've supplied an App Store Connect API key (then it's non-interactive too).

## Part 0 — Decide scope with the user first

Shipping a build consumes an EAS build and creates a public App Store Connect record on
first submit — outward-facing and not cheaply reversible. Before building, confirm:

- **Fresh build vs. reuse an existing finished build?** A fresh build picks up the
  latest `main`; reuse is faster but may be stale. Check history first:
  `cd apps/mobile && eas build:list --platform ios --limit 5 --non-interactive --json`.
- **Submit auth:** human runs `eas submit` (interactive Apple login) — the default — or
  they provide an App Store Connect API key for non-interactive submit.

Don't guess these; ask. (This matches the user's standing instruction to ask rather than
assume on irreversible/outward actions.)

## Part 1 — Verify the server URL (lesswhelmed.com)

The mobile production build must talk to `https://lesswhelmed.com`, and the prod server
must trust the app's `siriusapp://` auth callback. These are already set — confirm they
haven't drifted:

- `apps/mobile/eas.json` → `build.production.env.EXPO_PUBLIC_AUTH_BASE_URL` = `https://lesswhelmed.com`
- `.env.production` → `BETTER_AUTH_URL`, `NEXT_PUBLIC_BETTER_AUTH_URL`,
  `EXPO_PUBLIC_AUTH_BASE_URL` all = `https://lesswhelmed.com`, and
  `AUTH_TRUSTED_ORIGINS` contains `siriusapp://`

If a different prod URL is ever requested, change it in **all** of those places (the
single source of truth for dev hosts is `packages/auth/dev-hosts.js`, but the prod URL
lives in eas.json + `.env.production`). Note `apps/mobile/.env` holds the **dev** URL
(`https://sirius.local`) — leave it alone; it is not used by store builds.

## Part 2 — Preflight + build (automatable)

Run the bundled script. It generates the Prisma client (mobile typechecks transitively
pull in `@repo/*`), typechecks the mobile app, asserts a clean git tree, kicks the EAS
production build, and polls until it reaches a terminal state — printing the build URL so
the human can watch logs.

```sh
.claude/skills/ios-app-store-deploy/scripts/build-ios-prod.sh
```

Run it from the repo root. It is safe to re-run. If typecheck fails or the tree is dirty,
it stops before consuming a build — fix the issue at the source (don't work around it)
and ask before changing build config. If the EAS build itself **ERRORS**, open the
printed build-logs URL, read the failing phase, and fix the root cause — confirm against
the real log before changing anything.

## Part 3 — Submit to App Store Connect

Once the build is `FINISHED`, follow `references/submit.md` for the exact `eas submit`
steps: interactive Apple login, creating the App Store Connect app record on first
submit, backfilling `ascAppId` into `eas.json` so future submits are non-interactive, and
the manual metadata/"Submit for Review" work that only the App Store Connect web UI can
do. Hand these steps to the human unless they've provided an ASC API key.

## What "done" means

The skill's job is finished when a `FINISHED` production build exists and the human has
the submit handoff. Actual review submission is gated on Apple credentials + store
metadata and is the human's call.
