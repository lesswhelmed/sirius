## 4. QA — how to test

Ground rule (from `docs/qa/README.md`): **the database (or raw API response) is the assertion; the UI is only for navigation.** The **worker daemon must be running** for any ingest/archive scenario. Start the full stack interactively — `! bun run dev` (backgrounded it silently falls off :443 and breaks auth).

Standard psql helper (repo root):
```sh
set -a; source .env; set +a
PSQL_URL="${DATABASE_URL%%\?*}"          # strip ?schema= for psql
q(){ psql "$PSQL_URL" -tAc "$1"; }
```

### 4.5 Device / simulator gotchas

- **portless dev URL** `https://sirius.local` — run `bun run dev` interactively (`! bun run dev`); backgrounded it breaks auth. `sirius.localhost` 404s in LAN mode by design.
- **Sim CA trust**: the iOS Simulator doesn't inherit the macOS trust store (`bun run dev` adds portless's CA to the booted sim). Physical devices need the one-time iPhone CA-trust runbook (`bun run dev:proxy`).
- **Disable simulator autocorrect first** (else typed URLs get a QuickType suffix; "neutral" taps hit suggestion chips).
- **Keyboard Done**: iOS ignores `inputAccessoryViewID` on multiline; use the app's `KeyboardDoneButton` (dismiss via `label="Done"`, not a neutral coordinate).
- **agent-device limits**: sub-second debounce bugs unreproducible; on iPad the app is a centered card so header taps/edge-swipe-back are unreliable (verify via modal swipe-down). Prefer manual device testing for these flows.
- **True offline can't be faked on the sim** behind portless — test offline/outbox on a physical device in airplane mode.

## 6. Backwards compatibility & safe production deploy

**Verdict: ✅ the production server deploy is backwards-compatible.** Verified against the migration SQL and the mobile API client.

### 6.1 Migration safety (all recent migrations)

Every recent migration is **additive and rolling-deploy-safe**. New columns all have defaults or are nullable; new tables are purely additive; the only two `DROP` statements are **server-internal**:

- `DROP COLUMN "Post"."searchVector"` (`20260624130000`) — verified internal-only: typed `Unsupported("tsvector")` (`schema.prisma:49`), never selected/written by Prisma, queried only via raw SQL in `searchCorpus`. Zero client impact.
- `DROP INDEX "IngestSubmission_contentHash_key"` (`20260704120000`) — replaced by two stricter *partial* unique indexes; no data loss; dedup is server-internal (no client contract).

Representative additive changes: `Post.aiTreatment NOT NULL DEFAULT 'full'` (`20260709000100`), `user.termsAcceptedAt` nullable (`20260703103525`), `IngestSubmission.shareGroupIds TEXT[] DEFAULT '{}'` + `ALTER TYPE PostVisibility ADD VALUE 'GROUP'` (`20260627000000`), `flaggedAt`/`visibility` nullable (`20260626/20260624`). No `NOT NULL`-without-default, no rename of a consumed column. → **migrations can run in `db:migrate:deploy` before build/reload with no old-server breakage.**

### 6.2 API contract changes vs old clients

- **Additive & SAFE:** `posts/changes` deltas gained `aiTreatment`/`sourceSubmissionIds`/embedding fields — old clients ignore unknown JSON; nothing removed/renamed (`packages/db/src/posts.ts:709-725`, client `sync/events.ts`). New reflection endpoints + the `402` regenerate route are brand-new surfaces old binaries never call. Ingest gained optional `visibility`/`shareGroupIds`/`projectId` (defaulted server-side) — **no new required field**. Offline-sync wire format unchanged (client cursor keys are client-local). Auth sessions minted by old apps still validate (only `useSecureCookies`/additionalFields changed; no cookie-name/SameSite/domain change).

### 6.3 ⚠️ The one hard-break — Terms `403` → forced logout (scoped)

**Mechanism (verified in code):** `agreedOr403` returns `403 {"error":"terms-required"}` on every UGC write route for a user with `termsAcceptedAt == NULL`, and its own comment warns "clients must NOT auth-retry a terms-required 403" (`lib/session.ts:34,39-44`). But the mobile `runWithAuthRetry` treats `403` **identically to `401`** (`apps/mobile/src/lib/api.ts:143`) and, after `MAX_AUTH_RETRIES`, calls `signOut()` (`:175-188`). So a terms-`403` **force-logs-out any binary that lacks the terms-acceptance UI gate**.

**Blast radius (verified + owner-confirmed): ZERO live exposure.** The terms-acceptance UI (`ec541ce`, 2026-07-03) is an **ancestor of the 1.0.1 bump** (`bd48157`, 2026-07-06), so **1.0.1 — the live App Store version — carries the UI gate**, which front-runs the server 403 (the user accepts terms in the full-screen gate before any write fires). Only a pre-2026-07-03 (1.0.0-era) binary would be exposed, and **1.0.0 was rejected/never released** (owner-confirmed), so no such binary is in users' hands. The terms gate is already live in prod. **No deploy-time mitigation is required.**

**Reads are never gated** (`feed`, `posts/changes` are 401-only), so offline sync keeps working regardless — only *writes* are affected.

### 6.4 Degraded (not a break) — content-safety `"flagged"` status on old binaries

A content-safety-flagged submission gets terminal `status = "flagged"` (`packages/db/src/ingest.ts`). Old mobile `ingest-status.ts` only knows `pending|processing|completed|failed|skipped`, so `"flagged"` falls through to the default **"Queued"** label — the capture card appears stuck forever (never crashes). Newer builds map it correctly. Low impact; force-OTA the status mapping if a pre-flagged-status binary is live.

### 6.5 Safe-deploy sequence

The standard sequence is safe as-is:
```
git pull --ff-only → bun install → db:generate → db:migrate:deploy → build → pm2 reload
```
1. Migrations are additive → run before build/reload; no ordering constraint against old code.
2. Confirm `AUTH_TRUSTED_ORIGINS` still contains `siriusapp://` + the prod origin before `pm2 reload` (unchanged config, but auth would reject the mobile origin without it).
3. **Terms-`403` mitigation: NOT NEEDED** (owner-confirmed). The live store version 1.0.1 carries the terms gate and 1.0.0 was never released, so no pre-terms binary is in the wild. Proceed with the normal sequence. (Retained for the record: if a future deploy ever *introduces* a new hard-block gate, version-gate it or force a minimum-app-version so pre-feature binaries don't hit it — old clients turn a `403` into a forced logout.)
4. **Rollback:** code rollback (pm2 to prior build) is clean. Migrations are forward-only but harmless to leave (all additive). Do **not** re-create `IngestSubmission_contentHash_key` on rollback — old code tolerates the partial indexes.
