# Design: "Capture in Sirius" — native iOS App Intents → Shortcuts app

**Date:** 2026-06-20
**Author:** StormyMeadow (claude-code)
**Status:** Approved design — ready for implementation plan
**Scope:** `apps/mobile` only (Expo / React Native). No server, no `apps/web` changes.

## Goal

Expose a first-class **"Capture in Sirius"** action inside Apple's **Shortcuts app**
(and as a Siri phrase) so a user can capture text/links into Sirius from anywhere
on iOS without first opening the app. This is the *simple, extensible* first rung:
native App Intents that **open the app** and reuse the existing React Native
authenticated submit pipeline. Silent/background capture is explicitly deferred.

### Non-goals (v1)

- Silent/background submission (no app launch). Deferred — see "Extensibility".
- Image / file / audio / video capture from Shortcuts. The existing
  `expo-share-intent` share extension already covers shared media; App Intents v1 is
  **text-only** (URLs are extracted from that text).
- Android. App Intents are an Apple framework; Android App Actions are out of scope.
- Any change to `/api/app/ingest`, `submitMaterials`, or the auth layer.

## Why these decisions (locked with the user)

1. **Native App Intents**, not a user-built URL Shortcut — Sirius's action appears
   as a building block directly in the Shortcuts app, zero user setup.
2. **Open the app** on run (not silent background) — reuses ALL current submit + auth
   logic; no native networking or session-bridging code.
3. **One parameterized action** ("Capture in Sirius", single Text input) — smallest
   extensible base. `urlMaterialsFromText` already splits URLs out of free text, so one
   action handles both notes and links.

## Approach (and rejected alternatives)

**Chosen — inject App Intents into the _main_ app target via a local config plugin.**
App Intents declared in the main app bundle (iOS 16+) are auto-discovered by the system;
no separate extension/target and no extra code-signing. The `ios/` directory is
gitignored and regenerated by `expo prebuild`, so the Swift sources must be added by a
config plugin on every prebuild, never hand-edited.

- **Rejected — `expo-apple-targets`:** adds a dependency and targets separate
  extension bundles; unnecessary because App Intents live in the main target.
- **Rejected — hand-edit `ios/`:** wiped on every prebuild (gitignored, regenerated).

## Architecture / components

1. **`apps/mobile/plugins/with-capture-intents.js`** — local Expo config plugin.
   Uses `@expo/config-plugins` (`withDangerousMod` to copy Swift sources into the iOS
   project, `withXcodeProject` to register them in the **main app target's** Sources
   build phase). Idempotent across repeated prebuilds (skip if already added).
   `@expo/config-plugins` ships transitively with `expo` — **no new dependency**.
   Registered in `app.json` `plugins`.

2. **Swift sources** under `apps/mobile/ios-intents/` (copied by the plugin), all gated
   `@available(iOS 16.0, *)`:
   - **`CaptureInSiriusIntent.swift`** — an `AppIntent` with `openAppWhenRun = true` and
     one `@Parameter` `text: String`. On run it percent-encodes the text and opens
     `siriusapp://capture?text=<encoded>`.
   - **`SiriusShortcuts.swift`** — an `AppShortcutsProvider` declaring the phrase
     "Capture in Sirius" so the action surfaces in the Shortcuts app immediately
     after install (no first-launch requirement).

3. **`apps/mobile/src/app/+native-intent.ts`** — extend the existing
   `redirectSystemPath` to recognize the `capture` host/path on a `siriusapp://` URL and
   route it to `/capture`. (Today it only rewrites the `expo-share-intent` data URL.)

4. **`apps/mobile/src/app/capture.tsx`** — new screen. Reads the `text` query param,
   turns it into `Material[]` via the existing `urlMaterialsFromText` (URLs split out;
   remainder becomes a `note`), then presents the same confirm-and-submit UI used by
   `shareintent.tsx` (optional note field, submit button) and calls `submitMaterials`
   with the current `useSession()`. On success, navigates to the Queue tab.

## Data flow

```
Shortcuts app / Siri ("Capture in Sirius", text input)
  → CaptureInSiriusIntent (Swift, openAppWhenRun)
  → opens siriusapp://capture?text=<percent-encoded>
  → +native-intent.ts rewrites → /capture
  → urlMaterialsFromText(text) → Material[]
  → confirm UI → submitMaterials(materials, session)
  → POST /api/app/ingest (session cookie, submittedById attached)
  → row lands in Queue
```

## The extensibility contract

The stable spine is **deep link → `Material[]` → `submitMaterials`**. Future growth
costs nothing in the submit/auth layers:

- **New action** (e.g. a typed "Capture URL"): add a Swift `AppIntent` struct to
  `ios-intents/` and register it in `SiriusShortcuts`. If it carries a new payload
  shape, add a `Material` kind following the registry pattern documented at
  `apps/mobile/src/lib/materials.ts` (the handler-registry comment block near the top).
- **Silent/background capture** (deferred non-goal): swap a specific intent's
  `openAppWhenRun` for native networking. This is the *only* future work that touches
  native auth (getting the better-auth session out of JS SecureStore into a shared
  keychain/app group, or using the shared `INGEST_TOKEN`). The JS side is untouched.

## Auth & edge cases

- **Session reuse:** `/capture` uses RN `useSession()`. If signed out, it routes to
  sign-in (mirroring `shareintent.tsx`) and preserves the pending payload so the capture
  submits after login.
- **Empty / whitespace text:** show a friendly empty state; do not submit junk.
- **Oversized text:** query-param-sized payloads only in v1 (text). The Shortcuts UI
  naturally bounds this; if decoding yields nothing usable, fall back to the empty state.
- **Percent-decoding:** the screen decodes the `text` param defensively (already-decoded
  by the router vs. raw) so encoded URLs and unicode survive intact.
- **Confirm-then-submit (not auto-submit):** because the app opens anyway, v1 lands on a
  pre-filled confirm screen rather than submitting silently — safer and consistent with
  the share flow. (Auto-submit would belong to the deferred background variant.)

## Verification

- **Build:** Expo Go cannot carry native App Intents; build a **dev-client or preview**
  via EAS (the repo is already on the prebuild/dev-client workflow). `bun run
  verify:native-ai` is unaffected by this change.
- **Plugin sanity:** after a clean `expo prebuild`, confirm the Swift files are present
  in `ios/Sirius/` **and** listed in the main target's Sources build phase before
  relying on the action.
- **Manual (handed to the user, not sim-driven — per project preference):**
  1. After installing the dev-client build, open the Shortcuts app → the
     "Capture in Sirius" action appears.
  2. Run it with sample text containing a URL → Sirius opens to a pre-filled confirm
     screen → submit → a new row appears in Queue.
  3. Trigger the Siri phrase "Capture in Sirius" → same flow.
  4. Signed-out case → action routes to sign-in, then completes the capture.

## Risks & mitigations

- **`.pbxproj` source-file injection is the fiddly part.** Mitigation: keep the plugin
  tiny and idempotent; verify Swift files land in the main target's Sources phase after a
  clean prebuild before depending on it.
- **iOS deployment target:** App Intents require iOS 16+. All Swift is gated
  `@available(iOS 16.0, *)`; the `AppShortcutsProvider` simply doesn't surface on older
  OSes. Confirm the app's min iOS target during implementation.
- **Concurrent swarm on `main`:** coordinated via Agent Mail. Files to be touched at
  implementation time (`app.json`, `apps/mobile/plugins/*`, `apps/mobile/ios-intents/*`,
  `apps/mobile/src/app/+native-intent.ts`, `apps/mobile/src/app/capture.tsx`) must be
  reserved and committed by explicit path only.
