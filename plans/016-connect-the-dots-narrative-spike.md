## Why this matters

The product vision's flagship Insight-Engine moment — "this new article supports a
note you wrote last month" — is the single most demoable "the AI is thinking about
your corpus" feature, and its **expensive half is already built**. On every scene
recompute the worker writes post↔post kNN similarity edges to the `PostNeighbor`
table, and the listing page already surfaces neighbors as a bare "Related / via
<category>" list. The missing delta is a **narrative**: a one-line *why these two
relate* gloss generated by Gemini from an existing `(postA, postB, score)` pair. This
spike defines the smallest path from the existing plumbing to that narrative, so the
maintainer can decide whether to ship it. (High acquirer-demo value: turns a static
link list into visible synthesis. NOTE: the `docs/ROADMAP.md` Phase-3 "Next" proposes
building a *new* `PostLink` model + nearest-neighbor job — that already exists as
`PostNeighbor` + `scene/recompute.ts`; the roadmap under-credits shipped work here.)

## Current state (what already exists — the spike builds on this)

- **Model** — `packages/db/prisma/schema.prisma:484` `PostNeighbor` (populated):

```prisma
model PostNeighbor {
  id String @id @default(cuid())
  postId String   // post -> post edge
  neighborId String
  score Float      // cosine similarity
  ownerId String
  @@unique([postId, neighborId])
  @@index([ownerId]) @@index([neighborId])
}
```

- **Writer** — `apps/worker/src/scene/recompute.ts:47` calls
  `replacePostNeighbors(ownerId, neighbors)` on every scene recompute (enqueued after
  each ingest via `assign-org.ts`). Read helper: `getPostNeighbors(ownerId)` in
  `packages/db/src/scene-cache.ts:44` returns `{ from, to, weight }[]`.
- **Surface** — `apps/web/app/(public)/listing/[slug]/related-posts.tsx` already
  renders neighbors (via the scene client + `relatedPosts(scene, nodeId, 6)` from
  `@repo/embedding-scene/scene-queries`), showing each related post + "via
  <category>". This is where a richer "Connections" card would live.
- **The non-fatal Gemini exemplar to mirror** — the reflection stage
  (`apps/worker/src/pipeline/reflection/generate.ts`, persisted as `ReflectionPrompt`
  rows at `schema.prisma:605`): after classification, an **unmetered flash
  ridealong** generates per-post content, is **best-effort/non-fatal** (a failure
  never fails the ingest), is skipped for stubs/bearer, and has a kill switch
  (`REFLECTION_ENABLED`). A "Connect the Dots" gloss should follow this exact
  contract (a `CONNECT_DOTS_ENABLED` flag, non-fatal, unmetered, skip stubs/bearer).

## Steps

### Step 1: Decide persistence

Inspect `PostNeighbor` rows (`db:studio`) and decide where the gloss lives: a nullable
`gloss String?` (+ `glossModel`/`glossAt`) column on `PostNeighbor`, OR a separate
`PostConnection`/`PostNeighborGloss` table keyed by `(postId, neighborId)`. Weigh:
`replacePostNeighbors` **replaces all edges** on every recompute (`scene-cache.ts:25`)
— a column on `PostNeighbor` would be wiped each recompute unless the replace logic
preserves glosses for surviving edges. Document the trade-off and a recommendation.

**Deliverable**: the persistence decision + its interaction with `replacePostNeighbors`.

### Step 2: Define the generation trigger + contract

Specify when the gloss is generated: as a new **non-fatal stage after the scene
recompute** (where neighbors are freshly written) OR as a reflection-adjacent
ridealong per new post. Define the contract by mirroring the reflection stage:
`CONNECT_DOTS_ENABLED` kill switch, skip stubs/bearer, best-effort (never fails the
job), unmetered flash model. Specify the prompt shape: given two posts' titles +
excerpts + the cosine score, return one sentence explaining the relationship.

**Deliverable**: the trigger + the flag/metering/non-fatal contract, written down.

### Step 3: Define the render surface

Specify the "Connections" card on the listing page — likely an enrichment of
`related-posts.tsx` (replace/augment "via <category>" with the generated gloss when
present, fall back to the current behavior when absent). Owner-only vs visible-to-
readers is an open question (the current related list is owner-scoped via the scene).

**Deliverable**: the surface + fallback behavior + the owner-visibility question.

### Step 4 (optional): Thin, flag-gated prototype

If building a prototype, keep it entirely behind `CONNECT_DOTS_ENABLED` (default
OFF), reversible, and non-fatal. Prove the end-to-end path for ONE post's top
neighbor: generate a gloss, persist it, render it. Do NOT wire it on by default or
metering-gate it. Verify `bun run check-types` → exit 0 and (if a stage test is
added) `bun --cwd apps/worker test` → pass.

**Deliverable**: the dark prototype + a note on what's proven and what's left.

## STOP conditions

Stop and report if:

- `PostNeighbor` is empty / not actually populated in the target environment (the
  scene recompute may not have run) — the whole premise depends on it; report before
  building.
- Preserving glosses across `replacePostNeighbors` requires reworking the recompute's
  replace-all strategy (a bigger change than a spike) — document it as an open
  question, don't refactor the recompute here.
- The generation would need to be metered against the AI cap for cost reasons (unlike
  reflection) — flag it as a decision for the maintainer.
